从 SDK 到 Agent

探针形态的换代（2020 – 2022）

一、SDK 时代是怎么接的

第一代平台的采集方式只有一种：引一个 jar 包。

业务方在 pom.xml 里加一行依赖，在配置文件里写几行参数，探针就装上了。日志那条线更轻 —— 继承一下 Appender，改一行日志配置就行。

这套东西在头两年跑得很好。接入成本低，业务方不用学新东西，出问题也好排查 —— 代码就在自己的应用里，出栈一打就看得见。

但它有一个前提：应用是你自己的，你能改。

二、规模上来之后，四个问题

1. 版本碎片化

SDK 是编译期依赖。每个应用锁一个版本，升不升级由应用自己决定。

结果就是：平台上跑着十几个不同版本的探针。每个版本的埋点字段、上报格式、配置项都可能不一样。平台侧要么兼容所有版本，要么等应用升。

升级一个探针，等于走一遍所有应用的发版流程。 在几百个应用的规模上，一轮升级的绝对时间是以季度算的。

2. 语言栈扩张

第一代只有 Java。

后来业务方开始上 Python。要覆盖，就得再写一套 Python SDK —— 从零开始，跟 Java 那套除了数据格式以外什么都不共用。

每多一种语言，就多一套 SDK 的开发和维护。

3. 覆盖不到第三方调用

这是最要命的一条。

SDK 靠业务方在代码里主动调 API 来埋点。但调用链上大量的时间是花在框架和中间件上的：JDBC、Redis 客户端、HTTP 客户端、消息队列客户端。

这些调用写在依赖库里，业务方的代码里只有一行 redis.get(key)。他没法为这一行去改 Redis 客户端。

业务代码能埋，框架里的调用埋不了。 而调用链的价值恰恰在于把整条链路串起来 —— 断在中间就没什么用了。

4. 接入要改代码

日志那条线之所以好用，是因为它只要改一行配置。指标和链路做不到 —— 要加依赖、要写埋点、要改打包配置、要重新发版。

业务方的接入意愿直接跟改动量挂钩。改代码的接入，推进速度永远比改配置慢。

三、Agent 换掉的是什么

Agent 的形态：一个 jar 包，启动时挂在 JVM 上，通过字节码增强在运行时改写目标方法的入口和出口。

业务方要做的只有一件事：启动参数加一个 -javaagent:。

不引依赖、不改一行代码、不用重新打包业务逻辑（配置换个启动参数）。

变化在于接入的时机和位置：

SDKAgent
接入方式编译期依赖运行时挂载
改什么业务方改自己的代码增强目标类的方法
能覆盖的范围业务方主动埋的点所有挂到的框架调用
升级方式逐应用升依赖 + 发版换一个 jar、重启
多语言每种语言一套 SDK每种语言一套 Agent（机制不同）

从"改代码"变成"加一个启动参数"，这一条就解决了版本碎片化和接入意愿两个问题。

四、挂载方式

Java Agent 有两条挂载路径：

启动时挂载。 JVM 启动参数里的 -javaagent: 指定 jar 包，JVM 在 premain 里回调 Agent 的入口，此时业务类还没加载。这是主要方式。

运行时挂载。 通过 agentmain + attach 机制挂到已经跑起来的进程上，不用重启。排查问题时很方便，但有些类已经加载完了，增强窗口更窄。

我们的主路径是启动时挂载，运行时挂载用于临时排查。

增强的核心是方法入口和出口。 入口记录开始时间和上下文，出口记录耗时和结果，两头一夹就是一个 span。异常路径单独处理 —— 抛出异常也算出口。

五、增强范围

不是所有方法都能增强，也不是所有方法都值得增强。

判断标准两条：这个调用是不是跨进程的，以及它是不是在关键路径上。

落下来大概是这几类：

  • HTTP 客户端：知道下游是谁、耗时多少
  • JDBC：知道这条 SQL 打给哪个库、慢在哪
  • Redis / 缓存客户端：知道命中和耗时
  • 消息队列客户端：知道生产端和消费端怎么串起来
  • 线程池与异步调用：把跨线程的上下文传下去
  • 应用入口：Servlet、RPC 框架的入口方法，链路从这里开始

范围是逐步扩的，不是一次定的。 每加一类增强，都要评估它的开销和对框架版本的依赖 —— 增强一个高频调用的方法，开销是能看出来的。

六、配置下发

SDK 时代配置在应用侧，改配置要改应用的文件、要重启应用。

Agent 时代配置可以集中下发：Agent 启动时从平台拉配置，平台侧改完，Agent 下次拉取时生效。

能下发的包括：采样率、要增强的框架开关、要忽略的包名和方法名、上报的地址与批量参数。

这条改变的意义比看起来大：采样率可以按应用调、按时间调，出问题的时候临时提高某个应用的采样率，不用碰应用。

七、判断层：代价是什么

Agent 解决了 SDK 的问题，同时引进了两个新的。

增强框架类天生脆弱。

字节码增强依赖目标类的内部结构：方法签名、方法个数、调用顺序、字段名。这些东西不是公开契约，框架版本一升就可能变。

变了之后的失败方式很隐蔽：不报错，只是不再产生数据。平台上看是"这个应用没接探针"，排查起来要从框架版本一路查到增强规则。

（这个失败模式在开源社区的同类项目上也能看到 —— 有个基于字节码增强的方案，在框架版本升级之后静默失效，直到现在还没修。后面讲治理层的那篇专题会展开这个案例。）

问题排查变难。

SDK 出问题，栈是自己的代码。Agent 出问题，栈里多了一层"别人改过的字节码" —— 报错的行号可能对不上源码，异常可能出现在类加载阶段而不是执行阶段。

类加载器体系是新增的复杂面。 Bootstrap / Extension / Application 之外，容器和中间件还会造自己的 ClassLoader。增强一个类之前，要先确定它是被哪个 ClassLoader 加载的，以及增强后的类能不能被正确加载。

八、SDK 没有被取代的那部分

Agent 覆盖了框架调用，但业务语义是猜不到的。

"这个方法处理的是哪个客户的订单"、"这次请求命中了几个推荐位" —— 这类信息只有业务代码自己知道。

所以 SDK 没有下线，它缩到了业务埋点这一块：Agent 负责框架和中间件，SDK 负责业务自定义的指标与事件。

现在的形态是两者共存：框架调用靠 Agent 自动覆盖，业务语义靠 SDK 主动上报，两条数据在平台侧对上。

九、后来

换成 Agent 之后，接入的推进速度明显不一样了 —— 从"改代码"变成"加启动参数"，业务方的抵触小了很多。

但维护成本转移了。以前是维护 SDK 的 API 兼容性，现在是维护增强规则对框架版本的适配。框架升级一次，要验证一遍增强还成立。

这笔成本是永久的。它也一直影响后面每一代探针的架构选择 —— 包括 OpenTelemetry 接入时为什么不做增强、为什么把治理层挂在已有的 span 上（第 4 篇、第 5 篇）。
