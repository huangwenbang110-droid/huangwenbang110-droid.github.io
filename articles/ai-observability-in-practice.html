AI 可观测落地

第四代 · 观测 LLM 应用本身（2026 – 至今）

一、跟第 7 篇的分界

第 7 篇写的是用 AI 观测：大模型是手段，被处理的是传统系统的指标、日志、链路、告警。

这一篇写的是观测 AI：被观测对象是 LLM 应用本身，产出是轨迹、Token 成本、输出质量评分。

两条线的分界一句话：被观测的对象换了。

前者的数据来源和观测方法都有先例，后者没有 —— 因为 LLM 应用多出了几样传统 APM 里不存在的东西。

二、多出来的四样

1. Token 语义。

传统 APM 的指标是 QPS、耗时、错误率。LLM 应用多了一组：Token 用量、成本、首 Token 时间（TTFT）、每 Token 时间（TPOT）。

这几个指标在传统 APM 里没有对应物。尤其是 TTFT —— 一次 LLM 调用可能总共 8 秒，用户觉得"卡"，但真正让用户难受的是第一个字出来之前的那 3 秒。总耗时相同、TTFT 不同的两个实现，体验差别很大。传统 APM 看不见这个差别。

2. 内容本身。

传统 APM 里，请求参数和响应体是"可选的上下文"，一般只记长度和状态码。

LLM 应用里，Prompt 和输出就是主要观测对象。排查一个问题，看的不是"这个接口返回了 500"，是"这次它到底输出了什么"。

这一条带来的直接后果是脱敏问题 —— 内容里有用户输入、有业务数据、可能有敏感信息。

3. 工具调用。

Agent 会调工具、查检索、读数据库。这些中间环节在传统调用链里是"下游服务调用"，在 LLM 应用里是推理过程的一部分 —— 要能看到模型为什么调了这个工具、传了什么参数、拿回了什么。

4. 非确定性输出。

同一个输入，不保证同一个输出。

这意味着"对不对"没法用断言判断。传统监控里，"错误率"是一个明确的东西；LLM 应用里，"这个回答好不好"需要一套评估机制。

三、六个模块

需求梳理下来是六个功能模块。

1. 轨迹追踪

把一次调用当成一条链路：

输入 → 节点执行 → 工具调用 → LLM 调用 → 输出

如果是工作流编排（LangGraph 这类），节点执行是多层的 —— 每个节点可能自己又是一次 LLM 调用加几次工具调用。这跟传统调用链的树形结构是一样的读法。

这一段跟传统 APM 的调用链是同一件事，只是 span 的类型多了几种：模型调用、工具调用、检索、编排节点。

2. 性能监控

  • Token 用量：输入 / 输出 / 总量
  • 首 Token 时间（TTFT）
  • 每 Token 时间（TPOT）
  • 调用成功率与错误类型
  • 端到端时延

3. 成本分析

按 Token 用量乘单价，把成本归因到：应用、模型、调用方、时间。

这一块的价值很直接 —— 大模型调用是按量计费的，成本曲线跟调用量直接挂钩，而且很容易因为一个循环调用或者一次 Prompt 膨胀翻好几倍。没有按维度拆开的成本视图，涨上去了也不知道是谁涨的。

4. 质量评估

  • 准确性：回答跟预期是否一致
  • 幻觉率：有没有编造事实
  • 合规性：输出有没有触线

5. 调试工具

  • 复现：把某次调用原样重跑
  • 重跑：改 Prompt 或参数后再跑一次
  • 版本对比：同一个输入在 Prompt A 和 Prompt B 下的输出差异

这一块是 LLM 应用特有的刚需。 提示词改了效果变差，传统工具完全帮不上忙 —— 因为"效果"不是 200 或 500。

6. 集成能力

支持主流框架，接入要轻。

  • LangChain / LangGraph：框架本身已经在 emit span，接进来主要是配置
  • Dify 这类平台：通过编排层对接
  • 目标是一行业务代码都不用改

四、底座没有白建

需求文档里有一句关键判断：最关键的可观测要素主要是指标、链路。

这句话决定了这个方向的实现路径 —— 不重新造一套观测系统，而是在已有的指标与链路底座上加东西。

具体的复用：

传统 APM 已有AI 可观测的用法
调用链的树形结构直接用来承载轨迹（多出几种 span 类型）
跨进程上下文传播用来串起"应用 → LLM 网关 → 模型"
时序存储与查询直接存 Token 用量、TTFT、TPOT 这些指标
拓扑与依赖用来表示应用与模型、应用与工具之间的调用关系
告警规则引擎直接用来配成本异常、TTFT 劣化这类告警

所以真正要新建的东西不多：采集侧的 span 类型与属性、几个 LLM 特有的指标、内容处理链路、评估机制。

前面四年建的那套底座，在这一代直接派上了用场。这也是为什么 AI 可观测能在半年多的时间里跑出东西来 —— 不是在空地上开工。

五、缺口在底座之上

底座能复用，但缺的东西也很明确，而且是三类。

1. 采集侧：不缺数据源，缺处理

Java 侧的框架已经在 emit OTel 的 GenAI span 了，采集这一层不缺。

缺的是 span 上挂的东西：成本算出来存在哪、脱敏在哪做、异常调用怎么标。

2. 内容处理：一条全新的链路

内容一旦成为观测对象，就带来一串新问题：

  • 脱敏：内容里有用户输入、业务数据、敏感字段，出域之前必须处理
  • 体积：Prompt 和输出动辄几 KB，全量存下来成本不低
  • 结构：内容不是字符串，是结构化的消息数组（角色 + 内容段），脱敏要按段做
  • 合规：金融场景下，内容留存的边界要划清楚

这一条在传统 APM 里完全不存在，是这一代新增的工程量。

3. 评估：没有断言可用

非确定性输出意味着传统那套"阈值 + 断言"的告警方式基本失效。

"错误率超过 1% 就告警" 在 LLM 应用里要用什么替代？目前只能做趋势类告警（质量评分环比下降、某个模型输出长度异常、成本突增），做不到"这次回答是错的"。

这是最大的缺口，也是这一代最难的一块。

六、判断层：卡在哪

卡点一：语义约定还在演进

采集侧走的是 OpenTelemetry 的 GenAI 语义约定，但这套约定现在还是 Development 状态，属性名会变。

这直接影响自研的部分：所有自定义属性不能占用 gen_ai.* 命名空间（那个命名空间里的名字随时可能被官方占用），必须走自己的前缀。读别人的属性也不能假设只有一个版本的名字 —— 框架可能同时 emit 多代命名，取值要按"取第一个存在的"来做，不能相加。

这不是理论上的担心。 同一份数据在属性名上出现多代并存，是现在就能观测到的现象。

卡点二：成本要落在调用之后

Token 用量和内容要等一次调用结束才完整 —— 在调用进行中，你只知道有多少输入 Token，不知道输出会跑多长。

所以成本计算只能放在调用结束的时刻。

但调用结束的时刻拿到的是只读的 span（在很多观测框架里，span 结束回调收到的是不可变快照）。想往 span 上写成本，就得换一个能改的时机 —— 往导出的最后一环上挂。

这个坑我们踩了，具体在第 8 篇之后那篇专题里展开。

卡点三：脱敏要在最后一道关口上做

脱敏的位置很关键。

在采集侧做，漏掉其他来源的数据；在分析侧做，敏感内容已经落库了。

正确的位置是数据离开进程之前的最后一个环节。 只有在那里，你面对的是完整的、要出门的那一份数据。

卡点四：质量评估没有可信的标准

回归到第 4 个模块：准确性、幻觉率、合规性怎么算？

  • 人工标注最可信，但不可能全量
  • 模型打分（用一个模型评另一个模型的输出）可以全量，但评分本身的可靠性没有保证
  • 规则匹配只能覆盖格式类问题，覆盖不了"内容对不对"

目前这三种都在用，但没有任何一种能单独撑起"质量"这个结论。

七、开源项目落在哪两块

上面那些缺口里，有两块我拿出来做成了开源项目：

缺口项目对应模块
成本算出来没地方放、异常调用标不出来ai-observability-guard 的成本治理
内容要脱敏、且要在最后一道关口做ai-observability-guard 的内容脱敏

做法是：不碰框架的类，挂在已有的 OpenTelemetry span 上做加工。

理由在上一篇（第 2 篇）里写过 —— 增强框架类天生脆弱，框架版本一升就可能静默失效。既然框架已经 emit 了标准的 span，就没必要再去增强它，在 span 上加一层治理更稳。

项目还在开发中，等能跑起来再单独写一篇讲实现。

八、现在的状态

已经确定的

  • 底座能复用，不用重新造一套观测系统
  • 采集侧不缺数据，Java 框架已经在 emit，缺的是加工
  • 内容处理是全新工程量，脱敏、体积、结构、合规四件事都要做
  • 成本与内容加工的位置在 span 导出前，不在采集侧

还不确定的

  • TTFT / TPOT 的量级，以及什么样的阈值算"劣化"
  • 质量评估的可信机制（三种方法都有短板）
  • 语义约定稳定下来还要多久，这期间映射表要维护几轮

这一代跟 AIOps 那一代的处境一样：方向清楚，工程边界还在试。 这一篇先记到这里。

这两条线（观测 AI 与用 AI 观测）都还在走。整套演进线到这里是第四代，后面的事以后再说。
