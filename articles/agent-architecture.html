Agent 架构落地

Java 与 Python 两套 Agent 的实现差异（2022 – 2026）

一、为什么会有两套

Agent 不是一种技术，是一个概念：在运行时改写目标程序的行为，把观测逻辑插进去。

这个概念在不同语言里的落地方式完全不同 —— 因为每种语言给外部程序留的入口不一样。

Java 有虚拟机规范，规范里明确定义了 premain、agentmain、字节码格式、类加载机制。所以 Java Agent 有标准可循。

Python 没有虚拟机规范这一层。它没有"挂载 Agent"的官方入口，只能靠在 import 阶段替换对象来达到同样效果。

结果是：同一个目标，两套完全不同的实现，代码层面几乎不共用任何东西。

二、Java Agent：字节码增强

挂载

-javaagent:xxx.jar 启动参数，JVM 在业务类加载之前回调 premain。这时候能拿到一个 Instrumentation 实例，接下来所有增强都通过它做。

增强

核心是字节码转换器：注册一个 ClassFileTransformer，JVM 每加载一个类，就把它交给你改一遍。

实际实现一般不自写字节码操作代码，而是用 ByteBuddy 或 ASM 这类库 —— 前者提供声明式的匹配与插桩 API，后者是纯字节码汇编。

一次增强大概要做四件事：

  1. 匹配：判断这个类是不是我要增强的目标（类名、父类、实现的接口、注解、方法签名）
  2. 插桩：在目标方法的入口和出口插入代码
  3. 取上下文：入口把当前调用信息放进上下文（线程局部变量或显式传递）
  4. 上报：出口把这条 span 交出去

几个真实约束

类加载顺序决定增强时机。 要增强的类在 Agent 之后加载，才能被截到。如果某个类已经被加载了（早启动的框架、Bootstrap 类），要么提前挂载，要么就得走 retransform。

ClassLoader 体系比想象的复杂。 同一个类名可能被不同的 ClassLoader 加载出多份，增强时要确认改的是哪一份、改完之后引用它的人能不能看到。

增强要能安全失败。 插桩代码抛异常会让业务方法直接失败。所以所有观测逻辑都包在 try-catch 里 —— 探针出问题不能影响业务，这条是底线。 增强失败就退化成"这个类没有数据"，不能退化成"这个应用报错"。

三、Python Agent：Monkey Patching

Python 侧没有 premain，没有 Instrumentation，没有字节码转换器的标准入口。

能做到类似效果的只有一条路：在目标模块被导入时，把它的函数替换掉。

_original = module.func

def patched(*args, **kwargs):
    start = time.time()
    try:
        return _original(*args, **kwargs)
    finally:
        report(module, func, time.time() - start)

module.func = patched

这套做法叫 monkey patching。它不需要改业务代码，效果上跟字节码增强是一回事 —— 但机制完全不同：

Java AgentPython Agent
挂载入口premain / agentmain（规范定义）无标准入口，靠 import hook 或显式初始化
增强方式改写字节码替换运行时对象
生效时机类加载时目标模块导入时
生命周期规范保证完全取决于替换时机
卸载可以 retransform 还原只能手工换回去

Python 侧的四个具体难点

1. 时机比 Java 敏感得多。

Python 的 import 会缓存模块对象。如果目标模块在探针初始化之前就被导入了，再替换就得从 sys.modules 里找到它 —— 而且已经被别处 from xxx import func 拿走的引用是换不掉的（那是另一个名字指向旧对象）。

所以 Python Agent 基本都要求尽早初始化：在业务代码导入框架之前就装好。实际部署里靠启动脚本、sitecustomize、或者框架自己的初始化钩子来保证。

2. 替换会丢掉函数签名和元信息。

def patched(*args, **kwargs) 把所有参数吃掉了。任何依赖签名做检查的地方（装饰器、类型校验、Web 框架的参数绑定、依赖注入）都可能因此出问题。

要保住就得用 functools.wraps + inspect.signature 手工还原，每包装一个函数都要做一遍。

3. 异步是单独一套。

同步和异步要分别处理。async def 的函数包装之后必须还是协程（不能是普通函数返回协程），否则 await 直接报错。

而且上下文传递的机制不一样：同步用线程局部，异步要靠 contextvars —— 后者才是协程上下文里能正确传播的方式。

4. 进程模型不一样。

Java 是一个 JVM，多线程共享内存。

Python 用 gunicorn / uwsgi 部署时是多进程：master 进程 fork 出多个 worker。探针在 fork 之前初始化的状态会被复制过去，fork 之后各 worker 独立 —— 本地缓冲、采样计数、上报连接都要按进程重新处理，否则会出现多个 worker 报同一份数据、或者缓冲被重复写。

GIL 也是约束。 上报逻辑不能阻塞业务线程，必须异步化或者放独立线程 —— 但独立线程仍然抢 GIL。所以 Python 侧的采样和上报比 Java 侧更保守。

四、两套 Agent 里共用的东西

实现机制完全不同，但对上层来说是同一套数据模型。

两套 Agent 产出的 span 结构对齐：

  • 同一个 span 概念：名称、类型、开始时间、耗时、状态、父子关系
  • 同一套上下文传播规则：跨进程时透传的 header 字段一致
  • 同一套属性命名与语义

所以平台侧不需要区分这条链路是 Java 来的还是 Python 来的 —— 它看到的是同一种数据。

跨语言链路能串起来，靠的就是这一层对齐。 一个 Java 服务调 Python 服务，两边用同样的 header 传播上下文，平台侧拼出来的是一条完整的 trace。

这一层对齐是刻意做的，也是最花精力的部分 —— 它要求两套 Agent 的语义定义先统一，再各自实现。

五、判断层：为什么不能共用一套设计

问题其实反过来问更清楚：为什么不能把 Java 那套思路搬到 Python？

答案是不能。因为"字节码增强"在 Python 里没有对应物：

  • Python 没有可操作的字节码加载钩子（有 importlib 的 loader 钩子，但它是文件级的，不是类级、方法级的）
  • Python 的函数是运行时对象，可以被替换 —— 这是优势，但代价是没有被替换的引用换不掉
  • 没有 ClassLoader 体系，但有多进程 + 协程，复杂度换了个地方

所以两套实现不是"重复劳动"，是同一个目标在两种运行时上的必然解法。共用部分只能共用数据模型和语义定义，不能共用实现。

另一个现实：Java 是主线

Python 侧的探针一直比 Java 侧覆盖范围窄。原因是投入产出比 —— Java 应用是绝大多数，Python 应用集中在少数几块。

于是维护上的差别也很明显：Java Agent 的增强规则按框架逐类维护，Python Agent 主要是把几个主流框架（Web 框架、数据库客户端、HTTP 客户端）盖住。

这是资源分配的判断，不是技术判断。 后面接入 OpenTelemetry 的时候，这个差异又影响了一次决策 —— 因为 OTel 在 Java 侧的生态成熟度比 Python 侧好得多。

六、后来

两套 Agent 一直并行维护到现在。

真正让维护成本降下来的，是后面引入了 OpenTelemetry 的标准模型：不再自己定义 span 结构和跨进程传播格式，改用社区标准。 新语言接入直接走 OTel 的 SDK，不用再写第三套自研 Agent。

但存量那两套没有下线 —— 这也是为什么现在有两套协议同时在跑（第 5 篇）。
